What you actually need to understand

The mental model, in four sentences

A repository is a folder that remembers its whole history. A commit is one saved change, with a message and an author. A branch is a parallel line of history. A pull request is a proposal — “here are my commits, please merge them into your branch” — carrying a discussion, reviews, and automated checks, and it ends either merged or closed.

Odoo's branches are versions. This is the key.

  • master — the next unreleased version, where new development happens
  • 19.0, 18.0, 17.0 — released versions that still receive fixes
  • saas-19.4 and similar — the intermediate releases used by Odoo Online

So the branch a pull request targets tells you which version gets the fix. That one fact answers most of the questions you currently can't answer.

Reading a PR page: four tabs

  • Conversation — the description plus discussion. Read the first post and the last few comments.
  • Commits — the individual changes that make up the proposal.
  • Checks — the automated tests. Green tick passed, red cross failed, orange dot still running.
  • Files changed — the diff, and where you will spend most of your time. Red lines with - were removed; green lines with + were added.

Commit tags make commits scannable

[FIX] account: wrong tax on reverse charge invoices

tag · module · what it does

[FIX] bug fix · [IMP] improvement · [ADD] new feature · [REF] refactor · [REM] removal · [MOV] move or rename · [REV] revert. You can tell the module and the intent before reading a single line of code.

Forward-porting — the thing that confuses everyone

Odoo fixes a bug in the oldest supported version that has it, and the same fix is then carried forward into the newer branches. So one bug produces several commits, one per version. That is why “is it fixed?” always depends on which version and which build date — not just on whether the PR was merged.

The “fixed in PR #123456” recipe

  1. Open github.com/odoo/odoo/pull/123456
  2. Read the line at the top: “wants to merge N commits into 17.0 from …” — that's the target version
  3. Confirm the purple Merged badge, and note the date
  4. Open Files changed and read the diff
  5. Compare the merge date against the client's version and build date

The six git commands that pay off immediately

# history of one file
git log --oneline -- addons/stock/models/stock_move.py

# find the commit that introduced (or removed) a string
git log -S "You cannot validate a transfer" --oneline

# who last touched each line, and in which commit
git blame addons/account/models/account_move.py

# WHAT CHANGED IN A MODULE BETWEEN TWO VERSIONS  <- upgrade research
git diff 17.0 18.0 --stat -- addons/stock/

# read one commit in full
git show a1b2c3d

# WHICH VERSIONS CONTAIN THIS FIX   <- answers the client's real question
git branch -r --contains a1b2c3d

The last one is the direct answer to “is this fix in 18.0?”, and almost nobody in support knows it exists.

What you actually need to understand

The ORM sits between Python and the database

In Odoo you almost never write SQL. You write self.env['account.move'].search([...]) and the ORM turns it into SQL for you. A model is a Python class and also a database table. Its fields are class attributes and also table columns.

self is many records, not one

This is the single most common beginner mistake. self is a recordset — a collection. That is why the most common line in all of Odoo is for rec in self:. If you write code that assumes one record, it breaks the moment someone selects two rows and runs an action.

A real computed field

from odoo import models, fields, api

class SaleOrder(models.Model):
    _inherit = 'sale.order'

    margin_pct = fields.Float(
        string="Margin %",
        compute='_compute_margin_pct',
        store=True,
    )

    @api.depends('amount_untaxed', 'order_line.purchase_price')
    def _compute_margin_pct(self):
        for order in self:                     # self is MANY records
            cost = sum(order.order_line.mapped('purchase_price'))
            if order.amount_untaxed:
                order.margin_pct = (order.amount_untaxed - cost) / order.amount_untaxed * 100
            else:
                order.margin_pct = 0.0         # assign in EVERY branch

Three ways this goes wrong in the wild, all of which you will see in tickets:

  • Missing a field in @api.depends → the value silently never updates
  • Forgetting to assign in one branch → ValueError: Compute method failed to assign
  • store=True with incomplete depends → wrong numbers saved in the database, which is worse than no cache at all

Inheritance and super()

_inherit = 'account.move' extends an existing model rather than creating a new one. Calling super() runs the original method so your code adds behaviour instead of replacing it. Custom code that overrides create, write or unlink without calling super() correctly is a recurring cause of broken databases — and a recurring cause of broken upgrades.

Reading a traceback

Read it bottom up. The last line says what went wrong; the lines above are the path that got there. Then scan downward for the first line that mentions a custom module — that is almost always your suspect, not the core line that finally raised the error.

Track C

XML

Everything a user sees is XML: views, menus, actions, reports, data. Most customisation lives here, and so does most upgrade breakage — because a patch anchored to a core view stops matching the moment that core view changes.

Links

Odoo — Developer referenceGo to User interface → View architectures. MDN — XPathThe query language inside every view inheritance.

What you actually need to understand

A view is XML describing a screen

The types you will meet are list (called tree before the rename you already know about), form, kanban, search, pivot and graph.

You patch views, you never copy them

<record id="view_order_form_margin" model="ir.ui.view">
    <field name="name">sale.order.form.margin</field>
    <field name="model">sale.order</field>
    <field name="inherit_id" ref="sale.view_order_form"/>
    <field name="arch" type="xml">
        <xpath expr="//field[@name='amount_untaxed']" position="after">
            <field name="margin_pct" widget="percentage"/>
        </xpath>
    </field>
</record>

position can be after, before, inside, replace or attributes. replace is the dangerous one — it throws away whatever core put there, so it breaks as soon as core changes. Which is exactly what an upgrade is.

Fragile anchors vs stable anchors

Anchoring on a field name (//field[@name='amount_untaxed']) is stable, because field names rarely move. Anchoring on position (//page[3]) or on layout structure is fragile, because any reshuffle in core silently changes what your xpath points at.

The error you will see a thousand times

Element '<xpath expr="//page[3]">' cannot be located in parent view

Translation: the core view changed and this patch no longer matches. It is the most common single error in any Odoo upgrade, and now you know what it means.

External IDs

sale.view_order_form is an external ID — module.record. It is the stable name used to point at a record from elsewhere. These live in the ir_model_data table, and they are what breaks when a module is renamed or removed. noupdate="1" on data means “do not overwrite this on module update”, which explains why some data stubbornly refuses to change.

What you actually need to understand

How models map to tables

Dots become underscores: the model account.move is the table account_move. A many2one field is a plain integer column (partner_id). A many2many gets its own join table. A one2many has no column at all — it is just the reverse view of a many2one somewhere else.

The metadata tables are the whole game

  • ir_model — every model in the database
  • ir_model_fields — every field, including custom ones; state = 'manual' marks a field that Studio or a user created
  • ir_ui_view — every view, with its XML in arch_db
  • ir_model_data — the external IDs, linking XML names to real rows
  • ir_module_module — installed modules and their versions
  • base_automation, ir_act_server — automation rules and server actions, which is where Studio writes its logic

The first query an upgrade consultant runs

-- Every custom / Studio-created field in this database
SELECT  m.model,
        f.name     AS field_name,
        f.ttype    AS field_type,
        f.relation,
        f.store
FROM    ir_model_fields f
JOIN    ir_model m ON m.id = f.model_id
WHERE   f.state = 'manual'
ORDER BY m.model, f.name;

this is the audit. memorise it.

-- What is installed, and at which version
SELECT  name, latest_version, state
FROM    ir_module_module
WHERE   state = 'installed'
ORDER BY name;

Read-only discipline

Never UPDATE or DELETE on a client database. The ORM does bookkeeping that raw SQL bypasses entirely — computed fields, constraints, tracking, logging. Read with SQL, write with the ORM. Breaking this rule is how consultants lose clients.

Track E · three weeks, then stop

Studio

Not a speciality — table stakes. You learn it so you can recognise what clients have built and judge what must become real code. Studio changes are the main reason upgrades break, so this is reconnaissance for the next track, not a destination.

Links

Odoo — Studio documentationOne afternoon. It is not a deep subject.

What you actually need to understand

Studio writes to the same database tables a developer's module writes to — but as “manual” records, with no module to own them and no file in git. That is the entire problem in one sentence: a module can be versioned, reviewed, diffed and migrated. A Studio change cannot.

Studio can add fields, edit views, create automation rules and server actions, build reports and add approval rules. It stops at anything needing real logic — loops, external calls, complex conditions, performance work, or overriding a core method.

The judgement you are building is a three-way call on every customisation you meet: (a) this is fine as it is, (b) this should be a proper module, or (c) this should not exist, because the underlying process is wrong. Being able to make that call out loud, with reasons, is what separates you from someone who can click.

What you actually need to understand

An upgrade has two halves, and only one is your job

The standard half — core schema and core data — is largely automated by Odoo's own tooling. The custom half is your modules, the Studio changes, third-party apps and dirty data. That second half is the job, it is different in every database, and that is precisely why it resists automation.

What breaks, in order of how often you will see it

  1. xpaths that no longer match, because the core view moved
  2. removed or renamed fields and methods that custom code still calls
  3. Studio fields and automations with no module to own them
  4. third-party or OCA modules with no release for the target version
  5. existing data that violates a constraint which did not exist before
  6. performance collapse — a query that was fine on 100k rows is not fine on 5M

What clients actually pay for

Not the button press. They pay for certainty, and certainty is a set of documents: a pre-upgrade audit, a test migration, a regression test list, a cutover plan and a rollback plan. Produce those and you are selling risk transfer, which is why this work bills at the rate it does.
